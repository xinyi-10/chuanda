0.3 贯穿全程的三件 P0 铁律

无论走到哪一阶段，以下三件事必须从阶段二起就钉死，不允许后补：

  1. 数据隔离：所有涉及用户数据的 SQL 强制带 user_id（阶段二用 MyBatis 拦截器统一注入）。
  2. 金额精度：金额字段 DECIMAL(12,2) + Java BigDecimal + JSON 序列化为字符串，三处一致。
  3. 异步超时补偿：@Async 任务必须配超时检测 + 状态机终态，不允许「永久执行中」。

阶段一数据库搭建（地基）

目标：产出可执行的建表脚本，字段/索引/约束与方案一致，且已吸收审核报告的数据一致性改进（H6/M8/L4/L5）。

1.1 执行步骤

步骤关键动作依赖风险点
1.1确认数据库环境：MySQL 8.0 + utf8mb4无版本 <8.0 不支持窗口函数；字符集误用 utf8 致 emoji 乱码
1.2编写 schema.sql：建库 + 表 + 索引 + 约束1.1漏改下方「字段级修正」清单 → 后期返工
1.3编写 data.sql：默认分类、衣物标签字典1.2分类枚举自由文本（L5）致规则引擎失效
1.4本地执行验证：SHOW CREATE TABLE 核对1.3直接改已上线库、无备份
1.5记录数据库版本：脚本入 Git，编号 V1__init.sql1.4无版本管理 → 协作冲突

1.2 必须吸收的审核改进点（建表时直接落实）

编号问题落地做法
H6type 双重冗余流水表只保留 category_id，type 由分类派生；应用层校验一致性
M8逻辑删除 + 唯一约束缺失分类名唯一索引用 user_id + name + deleted 复合
L4异步任务状态机不完整async_task.status 增加 4=超时 5=取消；补 timeout_at
L5枚举用 VARCHAR 存自由文本season/style/category 建字典表或加 CHECK 约束
H5金额序列化表字段 DECIMAL(12,2)（库层）——Java/JSON 层在阶段二处理

1.3 验收标准（出口门禁）

  • schema.sql 可在干净 MySQL 8.0 一次性执行成功，无报错。
  • 所有表含 user_id / create_time / update_time / deleted 通用字段。
  • 金额字段均为 DECIMAL(12,2)，无 FLOAT/DOUBLE。
  • H6/M8/L4/L5 四项修正已体现在脚本中。
  • 种子数据可正常导入，默认分类可直接被前端渲染。
衔接：验收通过后产出 sql/schema.sql + sql/data.sql，作为阶段二的数据库连接依据。

阶段二项目框架搭建（工程骨架）

目标：跑通一个「能启动、能连库、能鉴权、统一响应」的空壳，并把三件 P0 铁律的基建全部铺好。

2.1 执行步骤（后端 + 前端可并行）

步骤关键动作依赖风险点
2.1初始化后端工程（SSM/Maven/WAR）1.x 通过JDK 版本隐患（见 2.3）
2.2初始化前端工程（Vue3 + Vite + Element Plus + Pinia + Axios）1.x 通过Element UI/Vue3 冲突（已纠正）
2.3配置数据库连接（HikariCP/Druid + 驼峰映射）1.5 + 2.1连接池参数不合理
2.4铺设 P0 基建（隔离拦截器 + 序列化 + 统一响应 + 全局异常）2.1见下方 P0 基建清单
2.5鉴权链路（登录/注册 + JWT + 拦截器）2.4H1 token 机制含糊，需定死
2.6异步框架（@EnableAsync + 线程池 + 超时补偿）2.4H4 超时检测不能后补
2.7接口契约（springdoc / Apifox）2.5M5 swagger 兼容坑
2.8联调打通（前端登录 → 接口 → 库全链路）2.1~2.7跨域配置（L2）

2.2 P0 基建清单（阶段二必须完成，不后移）

基建对应风险关键实现
数据隔离拦截器H2MyBatis 拦截器自动给「含 user_id 的表」注入 user_id 条件
BigDecimal 序列化H5Jackson 全局配置输出字符串；金额出参禁用 double

超时补偿任务H4定时扫描 status=1 且 now>timeout_at → 置「超时」

2.3 关键环境隐患（JDK）

  • 风险：IntelliJ IDEA 可能静默用 JDK 23 跑 Maven，而项目配的是 JDK 17，引发运行期异常。
  • 动作：启动时核对 pom.xml 的 maven.compiler 与 IDEA 的 Project SDK、Maven runner 三项一致为 JDK 17，并写进团队备忘。

2.4 验收标准（出口门禁）

  • 后端 mvn package 成功产出 WAR，Tomcat/Jetty 可启动。
  • 前端 npm run dev 可启动，页面正常渲染。
  • 登录 → 签发 token → 访问受保护接口全链路通。
  • 数据隔离拦截器生效（用越权请求验证会被拦）。
  • 金额接口返回字符串（非浮点）。
  • 异步超时补偿定时任务已注册并可用。
衔接：产出可运行空壳 + 接口契约文档，作为阶段三并行开发的「共同基准」。

阶段三编码实现（业务落地）

目标：按「鉴权 → 笔记 → 记账 → 穿搭」顺序实现业务，前后端在接口契约锁死后并行开发。

3.1 模块执行顺序与依赖

3.1 鉴权加固 ──► 3.2 笔记模块 ──► 3.3 记账模块 ──► 3.4 穿搭模块 ──► 3.5 前端页面联调
步骤关键动作依赖风险点
3.1鉴权加固（token 刷新/登出失效）2.5H1 无 refresh 则体验差

3.3记账模块（流水 CRUD + 统计）3.2H6 type 一致性校验
3.4穿搭模块（衣物库 + 天气 + LLM + 异步 + 兜底）2.6 + 3.3H3 prompt 注入 / M6 熔断限流

3.2 编码期必须落实的审核改进点

编号问题落地做法
H3Prompt 注入衣物名/备注拼入 prompt 前转义/角色隔离；输出只取结构化衣物 ID
M6外部依赖无熔断限流天气/LLM 各配独立线程池 + 信号量限流 + 超时 + 重试（≤2 次）+ 熔断
M1搜索性能明确数据量阈值，超过切 FULLTEXT（ngram）；加最小搜索长度
M3衣物删除后历史「死 ID」items_json 存快照（id+name+category 冗余）
M2轮询压力轮询加指数退避；结果查询走缓存，避免每 1s 打 DB
M5Swagger 兼容用 springdoc-openapi 或 Apifox 维护契约

3.3 并行 / 串行说明

  • 可并行：3.2 笔记、3.3 记账的前端页面可与后端接口并行（契约已锁）。
  • 必须串行：3.4 穿搭依赖 2.6 异步框架 + 3.3 的数据隔离经验；3.3 记账依赖 3.2 笔记验证过的数据隔离链路。

3.4 验收标准（出口门禁）

  • 每个模块 CRUD + 查询接口联调通过，统一响应格式正确。
  • 数据隔离在所有新接口生效（越权测试通过）。
  • 金额计算/统计结果精度正确（BigDecimal 全程）。
  • 穿搭异步链路跑通：正常 + LLM 失败兜底（source=2）+ 超时补偿。
  • 前端页面可完整操作，无阻塞性 bug。
衔接：产出完整业务代码，进入阶段四测试与验收。

阶段四测试与验收（质量闭环）

目标：用测试覆盖审核报告中缺失的测试策略（L1），并完成安全/性能/一致性专项验收。

4.1 执行步骤

步骤关键动作依赖风险点
4.1单元测试（金额、规则引擎、type 校验）3.x金额用 double 断言
4.2集成测试（异步状态机、鉴权全流程）4.1异步测试时序不稳定
4.3安全专项（越权、XSS、prompt 注入、CORS）3.x越权漏测（最高风险）
4.4性能专项（深分页、搜索、轮询压力）3.x深分页 LIMIT 100000,10
4.5验收 + 部署（Nginx + Tomcat）4.1~4.4L3 多实例与缓存一致性

4.2 必测清单（对应审核 L1）

必测项对应风险
金额计算 / 统计聚合H5、L6
规则引擎兜底逻辑H4 降级
越权访问（跨用户读数据）H2
异步任务状态机（成功/失败/超时/取消）H4、L4
逻辑删除后同名分类重建M8

4.3 验收标准（出口门禁）

  • 单元测试 + 集成测试全部通过。
  • 越权专项测试通过（无跨用户数据泄露）。
  • 金额全程精度正确，统计 percent 总和为 100%。
  • 异步任务无「永久执行中」残留。
  • 部署后 Nginx 反向代理 /api 正常，生产无 CORS 问题。
