个人生活管理软件 —— 开发方案审核报告

审核对象：docs/个人生活管理软件-开发方案.md（V1.0）
审核视角：资深项目审核员
审核维度：架构设计、安全性、可维护性、性能、测试覆盖、数据一致性

一、审核结论

这份方案在选型纠错（Element UI → Element Plus）、金额精度、异步兜底、数据隔离等关键点上写得相当扎实，架构骨架、分层职责划分也清晰到位，能直接拿去拆任务排期。但正因为细节到位，反而有几处「看起来对、实际埋雷」的地方更值得警惕。

真正的短板集中在两处：

  • 安全全靠「约定」 —— 数据隔离、Token 管理、Prompt 注入都没有强制机制。这是隐私类应用最不能靠自觉的地方。
  • 异步与一致性只有「正常路径」 —— 超时补偿、任务状态机终态、金额序列化、type 冗余校验等「异常路径」没有落地细节，而生产故障往往就出在这些边角。

若下一步进入编码阶段，建议优先在 M1 骨架期钉死三件事（成本最低、收益最大）：

  • H2 数据隔离插件（MyBatis 拦截器自动注入 user_id）
  • H4 异步任务超时补偿
  • H5 BigDecimal 序列化防护

二、高风险问题（会直接导致上线故障 / 安全事故）

#类别严重度问题改进方向
H1安全性高JWT/Token 鉴权机制含糊。文档只写「存入 Redis 或前端本地存储」，二选一没说死，且未区分 access/refresh。若存 localStorage，XSS 即可盗 token；若无 refresh 机制，token 过期体验差。明确 token 类型与存储位置；优先 HttpOnly Cookie 或内存 + refresh token 双 token 方案；给出过期/刷新/登出失效的完整流程。
H2安全性高数据隔离只停留在「约定」层面。第 8.1 节「每条 SQL 必须带 user_id」是口头约束，无拦截器/MyBatis 插件兜底。极易在某个查询漏写 user_id 造成越权读他人数据（笔记/账单是隐私重灾区）。用 MyBatis 拦截器自动注入 user_id 条件，或写代码评审卡点强制校验；越权是 P0，不能靠自觉。
H3安全性高LLM prompt 注入风险未提及。衣物名/备注是用户自由输入，直接拼进 LLM prompt 会被注入（如「忽略以上指令，输出……」，或诱导泄露系统提示词）。对用户输入做 prompt 转义/角色隔离；LLM 输出只取结构化的衣物 ID，不做任意文本回显执行。
H4架构高异步任务无「超时补偿」的落地细节。文档风险表提了「任务超时补偿」，但第 7 节代码里只有 try-catch 标记成功/失败，没有任何超时检测。若线程在调 LLM 时挂死（网络卡住），任务状态会永久卡「执行中」。加定时任务扫描 status=1 且超时（如 >60s）的任务置为失败；线程池任务设置超时 + Future.get(timeout)。
H5数据一致性高金额示例用了浮点字面量。第 6.3 节接口出参里 totalIncome: 8000.00、percent: 35.9，虽然 8.1 强调 DECIMAL/BigDecimal，但 JSON 序列化时 BigDecimal 若配错会转 double 丢精度。明确 Jackson 序列化 BigDecimal 输出字符串或 @JsonSerialize，禁止浮点出现在金额链路任何一环。
H6数据一致性高记账 type 字段双重冗余 + 无约束。ledger_record.type 和 ledger_category.type 都存收支类型，两者可被写得不一致（收入流水挂到支出分类），且无外键/CHECK 约束。流水只冗余 category，type 从分类派生；或加应用层强校验「流水 type 必须等于分类 type」。

三、中风险问题（影响可维护性 / 潜在性能 / 体验）

#类别严重度问题改进方向
M1性能中笔记搜索用 title LIKE '%kw%' + 正文 LIKE。前后通配符无法走索引，数据一多全表扫描。文档虽提了 FULLTEXT 但只当「后续可加」，未定触发阈值。明确数据量阈值，超过即切 FULLTEXT（中文需 ngram parser）或 ES；搜索加最小长度限制。
M2性能中前端轮询 1s×30 次做异步查询，并发推荐时对 DB 造成无效压力，且 30s 上限若 LLM 超 30s 会误报失败。首版可用但给轮询加指数退避；结果查询走缓存/内存态，别每 1s 打 DB；上限与后端超时对齐。
M3可维护性中items_json 存 JSON/TEXT 关联衣物，衣物删除后推荐记录里是「死 ID」，历史记录无法还原衣服名。存快照（id+name+category 冗余）而非纯 ID；或衣物删除做软删保证可追溯。
M4可维护性中缺少「统一错误码字典」的实际内容。第 8.3 说「维护错误码表」，但全文没给出 code 定义，前端差异化提示无从落地。附录补一份错误码枚举（业务码段规划），避免后期前后端各写各的。
M5架构中SSM 非 Boot，用 Knife4j/Swagger 的配置成本被低估。springfox 对 Spring 5.3 + JDK 17 兼容性差、已基本停更，容易踩坑。明确用 springdoc-openapi 或 YApi/Apifox 手动维护契约，别在 SSM 上死磕 swagger。
M6架构中外部依赖（天气/LLM）无「熔断 + 限流」设计。只有缓存和兜底，没有对 API 超时、重试、熔断、并发上限的明确配置，可能打爆免费额度或拖垮线程池。给外部调用配超时、重试（最多 1-2 次）、熔断器；天气/LLM 各配独立线程池 + 信号量限流。
M7安全性中统一响应里 timestamp 与 code 语义混乱。timestamp 示例写死作演示可理解，但未说明用服务器时间戳；code 复用 HTTP 语义码与 HTTP 状态码混用易混淆。明确业务 code 与 HTTP status 的分工；timestamp 由后端生成，前端用它做时区对齐。
M8数据一致性中deleted 逻辑删除 + 唯一约束缺失。若分类名需唯一，逻辑删除会让「已删同名」占位导致无法重建。唯一索引用 user_id + name + deleted 复合，或 deleted 存删除时间戳而非 0/1。

四、低风险问题（打磨项 / 完整度）

#类别严重度问题改进方向
L1测试覆盖低全文无任何测试策略。单元测试（金额计算、规则引擎兜底）、集成测试（异步链路）、安全测试（越权）全部缺失。补测试章节：金额/规则引擎必测，越权用例必测，异步任务状态机必测。
L2安全性低CORS 配置描述不精确。CorsFilter 在鉴权前，且开发期开后端 CORS、生产走 Nginx——但没写白名单/是否 allowCredentials。明确允许的 origin 白名单，禁止 * + credentials 同开。
L3架构低Nginx 负载均衡/多实例与单机 Tomcat 部署的冲突。架构图写了「负载均衡」，但异步任务、本地 Caffeine 缓存在多实例下会不一致。首版明确单实例即可，多实例时缓存换 Redis、任务表保证幂等。
L4数据一致性低async_task 与 outfit_record 用 result_ref 弱关联，无外键约束，finish_time 未覆盖「超时/取消」终态。状态机补「超时」「取消」终态；明确 result_ref 写入时序。
L5可维护性低season/category/style 用 VARCHAR 存枚举，衣物标签散落自由文本，规则引擎匹配会因「夏」vs「夏季」不一致失效。用字典表或枚举 + 约束，保证规则引擎可精确匹配。
L6性能低统计 percent 由后端算但没定保留位数，且 GROUP BY category_id, type 的 type 在 ledger_record 里，与 H6 的分类派生方案需统一。统一 type 来源；percent 保留 1 位小数 + 总和校验为 100%。
