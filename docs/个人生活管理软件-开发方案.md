# 个人生活管理软件 —— 开发方案（V1.0）

> 文档角色：开发组项目经理（PM）视角的落地方案
> 技术底座：Java + SSM（Spring 5.x + Spring MVC + MyBatis）+ MySQL + Vue3 + Element Plus
> 交付目标：一份可直接拆任务、可排期、可验收的技术方案

---

## 1. 项目概述

### 1.1 项目定位

一款面向个人的**轻量生活管理工具**，把「记笔记 / 记账 / 穿什么」三件高频小事收敛到一个入口，核心体验是**打开就能记、记完有反馈**。

### 1.2 目标用户与核心价值

| 维度 | 说明 |
|---|---|
| 目标用户 | 学生 / 年轻上班族，注重个人事务整理、经济自律与形象管理 |
| 核心价值 | 一站式（免切换多个 App）· 数据私有（自部署）· 智能（AI 穿搭推荐） |
| 使用频率 | 笔记 / 记账：每日多次；穿搭推荐：每日 1 次（早间场景） |

### 1.3 需求功能矩阵

| 模块 | 子功能 | 优先级 | 备注 |
|---|---|---|---|
| 笔记模块 | 创建 / 编辑 / 删除 | P0 | 基础 CRUD |
| 笔记模块 | 分类（多级 or 单级） | P0 | 建议单级起步，预留多级扩展 |
| 笔记模块 | 搜索（标题 + 正文） | P0 | 全文模糊检索，可升级全文索引 |
| 记账模块 | 收入 / 支出流水记录 | P0 | 金额、时间、分类三要素 |
| 记账模块 | 统计（按时间 / 分类汇总） | P0 | 月度收支、分类占比 |
| 穿搭推荐 | 衣物库维护 | P1 | 推荐的前提数据 |
| 穿搭推荐 | AI 智能推荐（天气 / 场合 / 已有衣物） | P1 | 依赖外部天气 API + LLM API |

> **PM 提示**：P0 三大件（笔记、记账）是「必须先跑通」的骨架，穿搭推荐属于「有了锦上添花」，建议放在第二个迭代，避免首版战线过长。

## 2. 技术选型

### 2.1 技术栈清单

| 层次 | 技术 | 版本建议 | 说明 |
|---|---|---|---|
| 后端语言 | Java | JDK 17 | 与你小组现有环境一致（注意 IDE 与 Maven 的 JDK 一致） |

| 连接池 | HikariCP / Druid | — | Druid 自带监控页，便于排障 |
| 前端框架 | Vue3 | 3.4+ | Composition API + `<script setup>` |
| UI 组件库 | **Element Plus** | 2.x | 见下方 2.2 修正说明 |

| 状态管理 | Pinia | 2.x | 轻量，替代 Vuex |
| 异步（后端） | Spring `@Async` + ThreadPoolTaskExecutor | — | 长耗时任务 |
| 缓存 | Redis（可选）/ Caffeine | — | 天气缓存、会话、热点数据 |
| API 文档 | Knife4j / Swagger | — | SSM 下用 springfox 或 knife4j |

### 2.2 选型修正（重要）

> ⚠️ **需求里写的「饿了么 UI（Element UI）+ Vue3」存在版本冲突。**
> Element UI 是**面向 Vue2** 的组件库，无法直接在 Vue3 上运行。
> **正确组合是 Vue3 + Element Plus**（Element UI 的官方 Vue3 版本，饿了么团队出品，API 风格一脉相承）。
> 方案按 **Element Plus** 推进；若小组已锁定 Element UI，则前端需降级为 Vue2，二选一，不能混用。

### 2.3 外部依赖

| 依赖 | 用途 | 建议服务 |
|---|---|---|
| 天气 API | 获取用户所在城市实时天气 | 和风天气 / 高德天气 / 心知天气 |
| LLM API | 生成穿搭建议 | 通义千问 / DeepSeek / 智谱 GLM |

> 两者**都必须做降级**：天气失败 → 用城市默认季节策略；LLM 失败 → 走本地规则引擎兜底。

## 3. 整体架构设计

### 3.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  表现层  Vue3 SPA (Element Plus + Pinia + Axios + Vite)   │
│          · 组件化页面  · 路由守卫  · 请求拦截器            │
└───────────────────────────┬─────────────────────────────┘
                            │ HTTP / JSON (RESTful)
┌───────────────────────────▼─────────────────────────────┐
│  接入层  Nginx（静态资源 + 反向代理 + 负载均衡）           │
└───────────────────────────┬─────────────────────────────┘
┌───────────────────────────▼─────────────────────────────┐
│  控制层  Spring MVC  @RestController                      │
│          · 参数校验(Validation)  · 统一响应封装  · 全局异常 │
│          · 登录鉴权拦截器(HandlerInterceptor)             │
└───────────────────────────┬─────────────────────────────┘
┌───────────────────────────▼─────────────────────────────┐
│  服务层  Spring Service (@Service / @Transactional)       │
│          · 业务编排  · 事务边界  · 缓存读写  · 异步调度     │
└───────────────────────────┬─────────────────────────────┘
┌───────────────────────────▼─────────────────────────────┐
│  持久层  MyBatis Mapper（XML + 动态 SQL）                 │
│          · Dao 接口  · ResultMap  · 分页                  │
└───────────────────────────┬─────────────────────────────┘
┌───────────────────────────▼─────────────────────────────┐
│  数据层  MySQL 8.0 (utf8mb4)  +  Redis(可选缓存)          │
└─────────────────────────────────────────────────────────┘
```

### 3.2 架构要点

| 关注点 | 设计 |
|---|---|
| 前后端分离 | 前端独立部署，后端只出 JSON 接口，通过 Nginx 反向代理打通 `/api` |
| 统一响应 | 所有接口返回 `{ code, msg, data, timestamp }`（沿用你现有项目 zcgl_study 的字段约定，前端零改造成本） |
| 无状态鉴权 | 登录后签发 JWT / Token，存入 Redis 或前端本地存储，拦截器校验 |
| 异步解耦 | 长耗时任务（AI 推荐、批量统计）走线程池，不阻塞请求线程 |
| 可观测 | 统一日志（Logback）+ 慢 SQL 监控 + 全局异常兜底 |

### 3.3 一次请求的完整链路（以「AI 穿搭推荐」为例）

```
浏览器 → Nginx(/api) → CorsFilter → 鉴权拦截器 → OutfitController.recommend()
   → OutfitService：① 组装上下文（天气 + 场合 + 衣物库）
                   ② 提交异步任务，立即返回 taskId
   → 线程池执行：调用天气API + LLM API → 落库推荐结果
   → 前端轮询 /api/outfit/recommend/result?taskId=xxx → 拿到结果渲染
```

### 4.1 后端模块（按包划分）

| 模块 | 包名建议 | 职责 | 关键类 |
|---|---|---|---|
| 通用基础 | `common` | 统一响应、异常、常量、工具类 | `Result`, `GlobalExceptionHandler`, `BizException` |
| 鉴权 | `auth` | 登录注册、Token 校验 | `AuthController`, `JwtUtil`, `AuthInterceptor` |
| 笔记 | `note` | 笔记 CRUD + 分类 + 搜索 | `NoteController`, `NoteService`, `NoteMapper` |
| 记账 | `ledger` | 流水 CRUD + 统计 | `LedgerController`, `LedgerService`, `LedgerMapper` |
| 穿搭 | `outfit` | 衣物库 + 推荐编排 + 结果查询 | `OutfitController`, `OutfitService`, `ClothingMapper` |
| 外部集成 | `integration` | 天气 / LLM 适配封装 | `WeatherClient`, `LlmClient` |
| 异步任务 | `async` | 线程池配置、任务状态管理 | `AsyncConfig`, `TaskService` |

### 4.2 前端模块（按目录划分）

| 目录 | 职责 |
|---|---|
| `src/api/` | 按模块拆分接口封装（note.js / ledger.js / outfit.js） |
| `src/views/` | 页面：笔记列表、记账看板、穿搭推荐 |
| `src/components/` | 复用组件：分类选择器、金额输入、图表卡片 |
| `src/store/` | Pinia：用户态、分类缓存、主题 |
| `src/router/` | 路由 + 登录守卫 |
| `src/utils/` | Axios 实例、拦截器、日期/金额格式化 |

### 4.3 职责边界（谁不该干什么）

- **Controller 只做**：参数接收与校验、调用 Service、返回结果。**禁止写业务逻辑**。
- **Service 负责**：业务规则、事务边界、外部调用编排。**禁止直接操作 HttpServletRequest**。
- **Mapper 只负责**：SQL 映射。**禁止在 XML 里做业务判断**。
- **异步任务**：只处理「可延后、耗时长」的逻辑，**不能承担必须强一致的主流程**。

```json
{
```

```json
  "data": {
    "taskId": 5001, "status": 2,
    "weather": "武汉 22℃ 多云",
    "outfit": {
      "items": [
        { "clothingId": 7, "name": "白色卫衣", "category": "上装" },
        { "clothingId": 12, "name": "牛仔裤", "category": "下装" }
      ],
      "advice": "今天 22℃ 多云，建议卫衣 + 牛仔裤…",
      "source": 1
    }
  },
  "timestamp": 1730000000000

```

**调用关系**

```
OutfitController.recommend()
  └─> OutfitService.recommend()

        └─ 提交线程池 @Async recommendAsync(taskId, req)
              ├─ WeatherClient.get(city)         ← 外部天气 API（带缓存）
              ├─ ClothingMapper.listByUser()     ← 查衣物库
              ├─ LlmClient.chat(prompt)          ← LLM API（失败→规则引擎兜底）
              └─ 写入 outfit_record + 更新 task(status=2/3)
前端：POST 拿 taskId → 轮询 result（间隔 1s，最多 30 次 / 或改 SSE 推送）
```

## 7. 异步处理设计

### 7.1 异步适用场景

| 场景 | 是否异步 | 理由 |
|---|---|---|
| AI 穿搭推荐 | ✅ 必须 | LLM 响应 2–10s，同步会拖死请求线程 |
| 批量统计 / 报表导出 | ✅ | 数据量大，可后台算完通知 |
| 笔记/记账单条 CRUD | ❌ | 毫秒级，异步反而增加复杂度 |

### 7.2 后端实现要点（SSM 环境，非 Spring Boot）

```java
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean("outfitExecutor")
    public ThreadPoolTaskExecutor outfitExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4);
        ex.setMaxPoolSize(16);
        ex.setQueueCapacity(100);
        ex.setThreadNamePrefix("outfit-");
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.initialize();
        return ex;
    }
}
```

```java
@Async("outfitExecutor")
public void recommendAsync(Long taskId, RecommendReq req) {
    try {
        taskService.markRunning(taskId);
        // 天气 → 衣物库 → LLM（含兜底）→ 落库
        taskService.markSuccess(taskId, recordId);
    } catch (Exception e) {
        taskService.markFail(taskId, e.getMessage());
    }
}
```

> **关键**：`@Async` 方法必须是**外部调用**（同类内部调用不走代理，注解失效）；异常必须**在方法内 try-catch**，否则任务状态会永远卡在「执行中」。

### 7.3 前端异步交互

| 方案 | 适用 | 说明 |
|---|---|---|
| 轮询（推荐首版） | 简单可靠 | 拿到 taskId 后每 1s 查一次，带最大次数限制 |
| SSE | 体验好 | 服务端 `SseEmitter` 推送，需处理断连重连 |
| WebSocket | 双向 | 对本项目偏重，不建议首版上 |

### 7.4 结果通知

- 前端以 `ElMessage` 提示「推荐生成中…」→ 完成后弹出结果卡片。
- 任务失败时给出可读原因（如「天气服务暂不可用，已使用季节默认策略」）。

## 8. 关键实现注意点

### 8.1 功能落地

| # | 注意点 | 说明 |
|---|---|---|
| 1 | **金额用 DECIMAL** | `ledger_record.amount` 必须 `DECIMAL(12,2)`，Java 侧用 `BigDecimal`，禁止 `double` 参与金额运算 |
| 2 | **逻辑删除** | 所有删除走 `deleted=1`，Mapper 查询统一带 `deleted=0` 条件 |
| 3 | **数据隔离** | 每条 SQL 必须带 `user_id` 条件，防止越权读他人数据 |
| 4 | **分类删除保护** | 分类下有笔记/流水时禁止直接删，或级联置为「未分类」 |
| 5 | **时间字段** | 存 `DATETIME`，前端统一按 `yyyy-MM-dd HH:mm:ss` 展示；统计按用户时区（GMT+8） |
| 6 | **AI 降级** | LLM 超时 / 失败 → 规则引擎（按温度区间 + 场合匹配衣物标签）兜底，`source=2` |
| 7 | **天气缓存** | 同城同小时结果缓存（Redis 或 Caffeine，TTL 30–60min），避免频繁打外部 API |

### 8.2 性能优化

| 方向 | 措施 |
|---|---|
| 数据库 | 关键查询建联合索引；统计用 SQL 聚合而非循环查；大表分页用「游标/延迟关联」避免深分页 `LIMIT 100000,10` |
| 缓存 | 分类列表、衣物库等低频变更数据加缓存；天气结果缓存 |
| 异步 | 长耗时任务线程池隔离（`outfitExecutor` 独立，防止拖垮主业务线程） |
| 连接池 | HikariCP 合理配置 `maximumPoolSize`（≈ CPU 核数 × 2 + 磁盘数） |
| 前端 | 路由懒加载；列表虚拟滚动 / 分页；Axios 请求防抖；图表按需引入 ECharts |
| 传输 | 开启 Gzip；图片走 CDN / 对象存储，不塞进数据库 |

### 8.3 前后端协作

| 关注点 | 约定 |
|---|---|
| 接口契约先行 | 开工前用 Knife4j/Swagger 锁定接口文档，前后端并行开发 |
| 统一响应格式 | 后端固定 `code/msg/data/timestamp`，前端拦截器统一处理 `code!==200` 的错误提示 |
| 错误码字典 | 维护一份错误码表，前端按码做差异化提示 |
| 跨域 | 开发期后端配 CORS，生产走 Nginx 同源反代（无需 CORS） |
| Mock | 后端未就绪时前端用 Mock 数据（Vite 插件）先跑通页面 |
| 命名一致 | 字段驼峰/下划线映射统一（MyBatis `mapUnderscoreToCamelCase=true`） |
| 版本管理 | Git 分支：`main` / `dev` / `feature-*`；提交信息规范 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Element UI 与 Vue3 不兼容 | 前端无法启动 | 改用 Element Plus（见 2.2） |
| LLM / 天气 API 不稳定 | 推荐功能不可用 | 双降级：缓存 + 规则引擎兜底 |
| SSM 下 `@Async` 配置失误 | 任务卡死 | 独立线程池 + 方法内 try-catch + 任务超时补偿 |
| 深分页性能差 | 列表卡顿 | 延迟关联 / 游标分页 |
| 金额精度问题 | 对账错误 | DECIMAL + BigDecimal 全程贯穿 |
| 外部 API 费用 | 成本失控 | 加缓存 + 限流 + 免费额度监控 |
