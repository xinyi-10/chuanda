个人生活管理软件
开发方案 V1.0

笔记 · 记账 · AI 穿搭推荐 —— 一站式个人事务管理工具。 基于 SSM 分层架构与 Vue3 前后端分离方案，覆盖架构、模块、接口、异步与落地要点。

后端 Java · SSM 数据库 MySQL 8 前端 Vue3 · Element Plus 异步 @Async · 线程池 智能 LLM + 天气 API

1项目概述

把「记笔记 / 记账 / 穿什么」三件高频小事收敛到一个入口，核心体验是打开就能记、记完有反馈。

🎯

目标用户

学生 / 年轻上班族，注重事务整理、经济自律与形象管理

💎

核心价值

一站式免切换 · 数据私有可自部署 · AI 智能推荐

⏱️

使用频率

笔记/记账每日多次；穿搭推荐每日 1 次（早间）

功能矩阵

模块子功能优先级备注
笔记创建 / 编辑 / 删除P0基础 CRUD
笔记分类P0单级起步，预留多级

📌

PM 建议：P0 三大件（笔记、记账）是必须先跑通的骨架，穿搭推荐放第二个迭代，避免首版战线过长。

架构要点

关注点设计
前后端分离前端独立部署，后端只出 JSON，Nginx 反代 /api 打通
统一响应{ code, msg, data, timestamp }（沿用现有 zcgl_study 约定，前端零改造）
无状态鉴权登录签发 Token/JWT，存 Redis 或本地存储，拦截器校验
异步解耦长耗时任务（AI 推荐、批量统计）走线程池，不阻塞请求线程
可观测Logback 日志 · 慢 SQL 监控 · 全局异常兜底

一次请求的完整链路（AI 穿搭推荐）

// 浏览器 → Nginx → CorsFilter → 鉴权拦截器 → OutfitController
OutfitController.recommend()
  └─▶ OutfitService.recommend()
        ├─ ① 生成 async_task(status=0)，立即返回 taskId
        └─ ② 提交线程池 @Async recommendAsync(taskId, req)
              ├─ WeatherClient.get(city)      ← 天气 API（带缓存）
              ├─ ClothingMapper.listByUser()   ← 查衣物库
              ├─ LlmClient.chat(prompt)        ← LLM API（失败→规则兜底）
              └─ 写入 outfit_record + 更新 task(status=2/3)
// 前端：POST 拿 taskId → 轮询 result（1s 间隔，最多 30 次）

职责边界（谁不该干什么）

Controller

只做参数校验 → 调 Service → 返回。禁止写业务逻辑

Service

业务规则、事务边界、外部编排。禁止直接碰 HttpServletRequest

Mapper

只负责 SQL 映射。禁止在 XML 里做业务判断

异步任务

只处理可延后、耗时长逻辑，不承担强一致主流程

7异步处理设计

异步适用场景

场景是否异步理由
AI 穿搭推荐✅ 必须LLM 响应 2–10s，同步会拖死请求线程
批量统计 / 报表导出✅ 建议数据量大，后台算完再通知
笔记/记账单条 CRUD❌ 不需要毫秒级，异步反而增加复杂度

后端线程池配置（SSM 环境，非 Spring Boot）

@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean("outfitExecutor")
    public ThreadPoolTaskExecutor outfitExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4);
        ex.setMaxPoolSize(16);
        ex.setQueueCapacity(100);
        ex.setThreadNamePrefix("outfit-");
        ex.setRejectedExecutionHandler(new CallerRunsPolicy());
        ex.initialize();
        return ex;
    }
}
@Async("outfitExecutor")
public void recommendAsync(Long taskId, RecommendReq req) {
    try {
        taskService.markRunning(taskId);
        // 天气 → 衣物库 → LLM（含兜底）→ 落库
        taskService.markSuccess(taskId, recordId);
    } catch (Exception e) {          // 必须捕获，否则任务永远卡在“执行中”
        taskService.markFail(taskId, e.getMessage());
    }
}
🔑

两个必踩的坑：
① @Async 方法必须是外部调用（同类内部调用不走代理，注解直接失效）；
② 异常必须在方法内 try-catch，否则任务状态永远卡在「执行中」。

前端异步交互方案

方案适用说明
轮询（首版推荐）简单可靠拿 taskId 后每 1s 查一次，带最大次数限制
SSE体验更好服务端 SseEmitter 推送，需处理断连重连
WebSocket偏重对本项目不必要，不建议首版上

8关键实现注意点

8.1 功能落地

#注意点说明
1金额用 DECIMAL字段 DECIMAL(12,2)，Java 用 BigDecimal，禁止 double 参与金额运算
2逻辑删除所有删除走 deleted=1，查询统一带 deleted=0
3数据隔离每条 SQL 必须带 user_id，防止越权读他人数据
4分类删除保护分类下有数据时禁止直删，或级联置为「未分类」
5时间字段存 DATETIME，统计按 GMT+8，前端统一格式化
6AI 降级LLM 失败 → 规则引擎（温度 + 场合匹配标签）兜底，source=2
7天气缓存同城同小时缓存（TTL 30–60min），避免频繁打外部 API

8.2 性能优化

🗄️ 数据库

联合索引；SQL 聚合代替循环查；深分页用「延迟关联/游标」避免 LIMIT 100000,10

⚡ 缓存

分类列表、衣物库等低频数据缓存；天气结果缓存

🧵 异步隔离

长耗时任务用独立线程池，防止拖垮主业务线程

🔌 连接池

HikariCP 合理配置 maximumPoolSize（≈ CPU核数×2+磁盘数）

🖥️ 前端

路由懒加载；列表虚拟滚动/分页；请求防抖；ECharts 按需引入

📦 传输

开启 Gzip；图片走 CDN/对象存储，不塞进数据库

8.3 前后端协作

关注点约定
契约先行开工前用 Knife4j/Swagger 锁定接口文档，前后端并行开发
统一响应后端固定 code/msg/data/timestamp，前端拦截器统一处理非 200
错误码字典维护错误码表，前端按码做差异化提示
跨域开发期后端配 CORS，生产走 Nginx 同源反代（无需 CORS）
Mock后端未就绪时前端用 Mock 数据先跑通页面
命名一致MyBatis mapUnderscoreToCamelCase=true，前后端字段风格统一
版本管理Git 分支 main/dev/feature-*，提交信息规范化
